Deck History

Every time you save a deck, MTGO Tools records that decklist as a version. You can look at any earlier version, see exactly which cards changed between two of them, and put an older one back on screen. Nothing has to be switched on and there is nothing to remember to do — saving is what records a version.

A save that changes no card records nothing, so saving twice in a row does not fill the history with empty entries. Reordering the lines of a decklist is not a change either.

Your decklist file itself is left alone. It stays the plain .txt that MTGO and the rental sites accept, with no version information written into it; the history is kept separately.

The Versions rail

The narrow column headed Versions sits between the deck tables and the Card Inspector, so the deck’s versions are visible while you are working on the cards. Each row is one version, newest at the top. Hover a row to see what that version was; click one to load it — a click in the rail moves the deck onto that version straight away, as described under Putting an older version back on screen below.

A deck with no history yet shows None yet.

The History tab

The History tab in the Deck Workspace is where a version is studied rather than just reached. It is split in two: the version graph on the left, and the selected version on the right under two sub-tabs, Decklist and Diff.

Clicking a node in the graph selects it. That fills the two sub-tabs and changes nothing on disk — it is a preview, not a move. (This is the one place the graph and the rail behave differently: the rail has nothing to preview into, so a click there is the move itself.)

A deck with no versions yet shows No version history yet — save the deck to create one.

Reading the graph

Newest version at the top, each one drawn above the version it came from. Each row carries a short summary of what changed and when it was saved. When a deck has more than one line of development the rows sit in separate columns — one column per line — joined back to the version they branched from. The current version is ringed.

The node menu

Right-click a version in the graph:

ItemWhat it does
Check out this version… Loads that version into the deck workspace and rewrites your deck file with it. See below.
Create branch here… Starts a named branch at that version without moving the deck onto it. A dialog (Create Branch) asks you to Name the new branch.
Set as diff baseline Pins that version as the one every diff is measured against, instead of each version’s own parent.

Comparing two versions

The Diff sub-tab shows what changed, card by card — cards added, cards removed, and counts that went up or down — for both the maindeck and the sideboard. A line above it says what the comparison is against:

LineMeaning
Comparing against parent… The default: each version is compared with the one it came from, which answers “what did this save change?”
Comparing against pinned baseline… You used Set as diff baseline, so every version you select is compared with that one version instead. This is how you measure a whole run of edits at once.

The first version of a deck has nothing before it, so its diff reads This is the first version — there is nothing to compare it against. Two versions whose cards match read No card differences.

If the deck was rooted at an archetype baseline, pinning that first version as the baseline is how you see everything your build does differently from the archetype.

Putting an older version back on screen

Use Check out this version… from the graph’s node menu, or click the version in the Versions rail. Either way MTGO Tools writes that version’s decklist to your deck file and reloads the workspace from it, and the status bar reports where the deck landed.

There is no confirmation prompt. Moving between versions is the point of the feature, and the version you were on is still a node on the graph, so the move is undone by making the opposite one. What is not recoverable is unsaved work: the cards on screen are replaced by the version you moved to, so edits you never saved are gone. Save first — that takes one click and makes a version of its own.

Branches

A branch is one line of development. Saving normally extends the line you are on.

Moving onto a version that is not the latest one on its line starts a new branch automatically, named after that version, and the deck is put on it. That is what stops a save made from an older version overwriting the versions that came after it: those stay exactly where they are, on their own branch, and your new saves go onto the new one. You can also start a branch deliberately with Create branch here….

The Branch picker at the top of the History tab switches between branches — and, as its tooltip warns, this rewrites the deck file on disk, exactly as checking out a version does.

Branches are never merged back together. Two branches that have diverged stay diverged, related only by the version they both grew out of.

Editing the deck outside the app

If you edit a deck’s .txt in a text editor and then open it here, MTGO Tools notices that the list is not one of the versions it holds and asks, under the heading Deck Edited Outside the App, whether to record it as a new version. It asks rather than guessing, because guessing either invents a version you did not make or buries an edit you did. It only asks for decks that already have a history — a deck opened for the first time is just a deck.

Where the history is kept

Each deck’s history is a folder of its own under deck_history in the MTGO Tools data folder, next to config. It is deliberately not under cache:

  • Uninstalling MTGO Tools does not delete it. Neither does clearing the application’s caches. Everything under cache can be downloaded or computed again; your deck’s edit history cannot, so it is kept out of the way of both.
  • Your deck files are untouched by it. The folder holds a private copy of the decklist for each version; the .txt in your deck folder never gains a companion file.

A deck is matched to its history by a hidden identifier fixed the first time it is saved, not by its name. So renaming a deck keeps its history, and two different decks that happen to share a name keep two separate histories.
